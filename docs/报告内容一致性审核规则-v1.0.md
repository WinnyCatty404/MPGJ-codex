# 报告内容一致性审核规则 v1.0

用途：作为测评工具后续开发审核功能的需求与规则依据。

## 1. 审核目标

以现场测评的结果记录、对应测评判定和有效证据为主要核对依据，审核以下六个位置是否准确表达同一事实、是否有结论依据，以及问题与建议是否对应：

1. 单元测评结果分析。
2. 整体测评分析。
3. 风险分析。
4. 评估结论。
5. 总体评价。
6. 安全问题及改进建议。

一致性不等于文字相同。允许归纳、合理简称和不同精度的表达，但不得改变关键事实、扩大适用范围、遗漏影响结论的重要问题，或把未知状态写成已证实事实。

现场记录不是绝对正确答案：记录自身矛盾、判定不清、对象关联不明时，先提出基础数据核查意见，再将依赖该记录的检查标为待确认。多数段落采用同一种表述，也不能作为判定该表述正确的理由。

主范围是人工填写、导入报告原文、自动生成后人工修改的描述。未修改的自动生成字段可以作为比较依据，其与输入不一致时归类为数据或生成同步问题。图片/代码证据复核作为可选扩展，正文一致性审核不默认完成证据真实性或技术实现审核。

## 2. 六个位置的核对要求

| 位置 | 主要核对依据 | 必查内容 | 允许的差异 |
|---|---|---|---|
| 单元测评结果分析 | 对应对象的结果记录、各维度判定及指标汇总 | 对象、技术事实、参数、缺陷、判定维度、最终结论 | 多个对象可以综合概括；对象级与指标级结论不要求字面一致 |
| 整体测评分析 | 各单元结果、跨层关系及修正/弥补依据 | 依赖对象、实际保护范围、跨层参数引用、修正前后状态 | 经有依据的整体分析形成不同结果；必须保留推导链，不能伪装成现场原始结果 |
| 风险分析 | 已确认问题、对应保护属性及相关缓解措施 | 风险是否有问题依据、风险方向、对象范围、缓解措施是否实际存在 | 风险是推断，允许出现“可能泄露”等不在原始记录中的推理；不得把可能后果写成已发生事件 |
| 评估结论 | 有效单元/整体结果、综合得分、风险清单及适用结论规则 | 系统级结论、数字、风险等级/数量、结论依据和措辞 | 系统级“基本符合”与个别指标“不符合”可能同时成立；不能直接与一个对象结论比较 |
| 总体评价 | 全部相关单元事实及重要问题 | 关键事实准确、问题覆盖、范围完整、无依据新增 | 可省略图号、重复细节及非关键参数；概括不能改变评价方向 |
| 安全问题及改进建议 | 未满足要求的对象、指标、具体缺陷及风险 | 问题与记录对应、建议针对缺陷、现状与拟采取措施分开 | 建议算法/产品不同于现状正常；建议不是现状已整改的证据 |

评估结论及整体分析若缺少可执行的标准/版本规则，只做描述与现有结果一致性检查，不由语言模型推导法定结论、风险等级或评分。

## 3. 数据准备与关联

### 3.1 必要输入

- 项目ID、系统名称、测评等级、采用标准版本、报告版本、取证时间。
- 层面ID、指标ID、对象ID和名称、所属子系统、关联数据类别、保护用途。
- 现场记录原文、A/D/K等维度标记、对象结论及其来源、评分和适用状态。
- 六个报告位置的有效原文、结构化结论、指标/对象关联及版本。
- 整体分析的依赖关系、修正/弥补依据、前后结果；没有时标记缺失。
- 图号/证据ID、资产和产品信息；仅按需读取图片和代码。

每一字段保存来源：`manual`（手填）、`imported`（报告导入）、`generated`（自动生成）、`generated_edited`（生成后人工修改）、`unknown`（无法确定）。保存导入批次、原始文本、当前修改版本；不得把所有reportTexts字段一律判为人工文本。

### 3.2 关联原则

基本比较键：项目＋有效报告版本＋层面＋指标＋对象＋保护用途＋时间/连接范围。

优先使用对象ID、指标ID和明确绑定。名称归一化只清理空白、全半角和标点；别名需要上下文证据。名称含“互联网端/申请端/群众端”时不可擅自删除后合并。

另建关联关系：子系统→业务端→访问通道、数据→所属应用→存储位置、设备→远程管理路径、产品/服务→提供的密码操作。跨层检查沿关联关系展开，禁止全报告搜索到任意算法就直接比较。

无法关联、导入未匹配、原文缺失、版本混用应形成数据问题。依赖检查返回“无法核对”，不根据缺失推定符合或不符合。

### 3.3 事实提取

每个事实单独保存：对象、行为、是否实施、是否合规、证据是否充分、协议/版本、算法/参数、用途、量词范围、时间、条件、原文定位。

区分：已实施／未实施／无法确认／未提供证据／计划／建议／要求；支持的版本与实际协商的版本；传输与存储；应用层与网络层；技术存在性与测评合规性。

结论类型保留原始标签：符合、部分符合、不符合、不适用、未测评、缺失。系统级评估结论独立建字段，不能映射成同一种对象级标签。

## 4. 规则目录

明确冲突只在对象、用途、范围和版本对应可靠时成立。其余返回疑点或信息不足，不自动认定专业测评错误。

| 编号 | 审核规则 | 触发条件 | 误报例外/处理方式 |
|---|---|---|---|
| C01 | 对象结论一致 | 同一对象指标的有效判定在不同位置明确相反 | 先区分原始结果、修正结果和汇总结果 |
| C02 | 维度判定一致 | A/D/K等标记与对应维度描述相反 | 有效性符合、算法合规性不符合可同时成立；不从某个维度直接推断最终结论 |
| C03 | 汇总结论依据 | 单元/整体结论缺少对应对象结果或与有效汇总相反 | 不采用“多数对象符合所以整体符合”的自创算法；按已有获认可规则或人工复核 |
| C04 | 肯定否定一致 | 同一措施被写成采用与未采用、提供与未提供 | 否定必须绑定其对象、动作、合规限定和时间 |
| C05 | 存在性与合规性分开 | 已写具体加密措施，又笼统写未采用任何密码技术 | “未采用合规密码技术”可能与现状一致；不得自动更改符合性结论 |
| C06 | 协议版本一致 | 同一次连接/用途的实际版本不同 | TLS1.2/TLSv1.2可归一；TLS1.2/TLS1.3不同；不同对象或测试时间另行核对 |
| C07 | 算法参数一致 | 算法、密钥长度、模式、套件或套件代码相反 | AES128/AES256不能合并；不同对象可使用不同参数 |
| C08 | 简称与省略 | 已给出的关键参数在另一处省略，身份或机制难以确定 | AES-256-GCM/AES_256_GCM可归一；AES未给模式不直接判冲突；信息不足不同于已确认一致 |
| C09 | 技术作用一致 | 加密、签名、MAC、哈希、握手派生等作用被混淆 | 名称包含某算法不代表它承担所有作用；需机制或证据支撑，不能仅看套件后缀 |
| C10 | 产品/证书身份一致 | 同一产品型号、编号、版本或证书归属出现差异 | 简称须有身份依据；不凭编号格式猜哪个值正确；客户端与服务端证书分开 |
| C11 | 多对象分配一致 | “分别/均/其中”等描述把算法、缺陷或结论分给错误对象 | 拆成对象级事实；不能只对比段落中的算法集合 |
| C12 | 对象范围一致 | 某对象缺陷被扩大成全部，或概括后改变关键覆盖范围 | 合理概括可省略重复细节，缺少提及不等于未实施 |
| C13 | 记录内部一致 | 一条记录的主语、对象、参数或肯否互相矛盾 | 相同配置和共享证据可以存在，复制相似不等于错误 |
| C14 | 证据状态不变 | 未核实/未提供记录被改写成未实施，制度存在被写成已执行 | 判定不符合也不自动证明措施不存在 |
| C15 | 时间与有效期 | 有效性、实施先后或证书日期与实际取证时间冲突 | 历史报告不按今天比较；工具更新日期须核对来源 |
| C16 | 跨层引用一致 | 应用层引用的通道、参数或图号与对应网络对象不同 | 多路径、不同测试可能解释；先确认关系再比较 |
| C17 | 整体分析可追溯 | 声称依赖、弥补或修正，但缺少关联结果、范围或依据 | 原始不符合与修正后部分符合并非必然矛盾；不能把评分修正写成已经整改 |
| C18 | 不适用/未测评一致 | 不适用、未测评、空白与正式结论混用 | 不适用需要理由；未匹配对象先报解析问题 |
| C19 | 问题覆盖 | 已确认的重要缺陷在总结/问题章节被遗漏或无依据淡化 | 允许合并同类问题；按指标、对象和实质缺陷判断覆盖，不要求逐字出现 |
| C20 | 新增事实有依据 | 总结或风险新增算法、产品、已实施措施、对象或事件 | 可引用其他有效证据；“可能发生”是风险推断，不按新增已发生事实处理 |
| C21 | 风险方向一致 | 机密性问题被写成纯完整性问题，或风险与缺陷关系不清 | 联合风险可存在，需解释关联；提示复核而非只按关键词判错 |
| C22 | 缓解措施真实 | 风险分析把计划或建议措施当作已实施的缓解条件 | 跨层现有措施可以缓解风险，但不自动消除对象原有缺陷 |
| C23 | 建议针对问题 | 建议对象、用途与问题无关，或遗漏关键整改方向 | 提出替代算法不构成参数冲突；实现方案优劣另行专业评审 |
| C24 | 现状与未来分开 | “建议/计划/应采用”被当成当前措施或整改完成 | 将未来措施与现场事实分开；必须有整改后证据才能更新事实 |
| C25 | 评估结论支撑 | 系统级结论、得分、风险表述与有效计算/清单不一致 | “无高风险”不等于“无安全问题”；缺少计算规则时只作数据一致性检查 |
| C26 | 测评范围一致 | 六处文字混用不同等级指标或引入范围外要求 | 以实际标准版本和测评范围确认，不从标题缺失直接认定不适用 |
| C27 | 数据版本/同步 | 当前编辑、导入快照、模板值或导出内容存在未解释差异 | 明确最终导出取值；历史版本不作为同版本冲突；重复存储不是独立证据 |
| C28 | 证据支撑充分性（扩展） | 仅凭长度/界面/函数定义就声称算法、完整性机制或部署有效 | 读取完整代码/证据链；缺少上下文标记不足，不直接断言未实施 |

## 5. 技术事实归一化示例

| 原文组合 | 归一化或判断 |
|---|---|
| TLS 1.3、TLSv1.3、TLS1.3 | 同版本写法 |
| AES_256_GCM、AES-256-GCM、AES256_GCM | 算法AES、密钥256位、模式GCM |
| AES256、AES_256_GCM | 密钥长度一致；第一处模式未知，不直接判完整一致或冲突 |
| AES_128_CTR、AES-256-CTR | 同一对象同一连接时密钥长度冲突 |
| SHA256、HMAC-SHA256 | 不能作为完全同义机制；前者可能是省略，需上下文 |
| 系统支持TLS1.2和1.3、此次协商TLS1.3 | 不矛盾 |
| 应用层未独立加密、网络层使用HTTPS加密 | 不矛盾；概括时应保留层面限定 |
| 建议使用SM4、现状使用AES | 不矛盾 |
| D=√、A=×、K=× | 维度分别判断，不能按三个符号自行确定最终结论 |

算法词典用于自动识别常见技术名称、操作类型及参数形式，结合上下文扩展。用户无需逐个登记报告中出现的全部算法。产品身份可利用项目已有资产数据，但不以用户维护完整组件清单为前置条件。

## 6. 审核执行流程

1. 固定本次审核的有效版本、范围及字段来源；检查解析完整性。
2. 按指标和对象收集现场记录、判定及六处关联描述；先检查现场自身。
3. 提取事实和结论，名称归一；为每个事实保存原文位置。
4. 执行明确字段与参数检查，再作范围、遗漏、风险、建议等语义检查。
5. 对需要证据或推导依据的问题标记待确认；按需触发截图/代码复核。
6. 输出审核清单，由审核人员定位修改或确认合理差异；修改后复核关联条目。

规则引擎负责版本/数值、显式结论及绑定检查。语言模型辅助拆分长段落、识别否定范围、对象范围与语义关系，但须输出原文依据，不能凭生成解释确认技术实现、评分或合规结果。

同一字段的多处副本应避免形成重复证据；多个规则可以关联同一审核意见。具体问题合并粒度属于后续产品配置，“最多报一次”只是系统名称，不设置“每种问题只报一次”等固定限制。

## 7. 审核结果结构

建议区分问题类型：`content_conflict`、`semantic_suspect`、`insufficient_information`、`data_link_issue`、`version_sync_issue`、`evidence_review`。

明确字段冲突可设高优先级；语义疑点及重要覆盖缺失设中优先级；非关键省略设低优先级。优先级是审核处理顺序，不是安全风险等级。匹配可靠性与判断可靠性独立保存；无法匹配返回无法核对。


示例位置范围仅为格式展示，真实执行须验证引用确为该版本字段的子串，约定范围使用UTF-16偏移或其他统一编码单位，禁止模型编造定位。应保存具体record-key、表格行列或证据ID，不使用页面文字作为唯一定位依据。

处理状态：待确认、确认需修改、合理差异、证据不足、数据关联问题、已解决。保存处理人、理由和版本；源文本改变后原处理意见标记待复核，不永久屏蔽类似问题。

界面至少显示两处原文、差异项、原因、所属对象和指标，并可跳转现场记录及目标章节。对遗漏/新增问题显示已搜索范围，避免让用户以为整份报告都已检查。

## 8. 开发验收案例

| 案例 | 预期 |
|---|---|
| CIM：同一应用通道记录采用AES128，问题描述未采用AES128 | 提出肯否冲突；保留“未采用国密算法”作为不同限定 |
| 数智组工：甲通道AES128、乙丙通道AES256，报告分别正确描述 | 不报参数冲突 |
| 数智组工：江河汇才应用层引用AES128而已绑定网络通道AES256 | 提出跨层参数疑点；关联不足时返回无法核对 |
| 数智组工：设备身份鉴别单元部分符合、有效汇总不符合 | 提出结论/版本核查，不自动改结论 |
| 基层在线：第三方存储无法确认，风险写明确未实施 | 提出证据状态改变 |
| 最多报一次：同一设备TLS1.2与TLS1.3 | 提出版本冲突 |
| 最多报一次：同一SSH对象AES128与AES256 | 提出密钥长度冲突 |
| 使用RSA加密但未采用合规密码措施 | 不以存在RSA直接判符合；否定不带合规限定时提示复核 |
| 一个对象不符合、其他对象符合，单元部分符合 | 核对汇总依据，不直接报对象级与汇总结论冲突 |
| 风险分析提出“可能泄露”，现场未发生泄露 | 不报新增已发生事件 |
| 建议采用SM4，现场AES | 不报参数冲突 |
| 导入对象未匹配产生未测评，原文存在结论 | 报数据关联问题，暂停依赖它的实质结论检查 |
| 整体分析有有效修正依据，修正后结果不同于现场 | 展示推导关系，不判无条件结论冲突 |
| 系统基本符合，同时有若干指标不符合 | 不直接冲突；仅按有效系统级依据核对 |

四份样本中的实例来自当前工具解析数据，不能未经原报告核查就当作原报告最终错误标签。建立验收集时需由审核人员确认问题和合理差异，并保留未用于规则整理的新报告做独立试审。

## 9. 建议开发顺序

第一阶段：字段来源、版本与对象关联；明确结论、肯否、协议版本和算法参数；定位与人工处理闭环。

第二阶段：六处问题覆盖、跨层依赖、风险方向、建议针对性、系统结论与有效计算结果的核对。

第三阶段：按审核疑点调用代码/截图复核，增加代码调用、对象范围、验证流程及密码服务来源的证据审核。

当前文档只定义审核功能，不实现业务代码，不自动修改项目数据、报告描述、评分或测评结论。
