# BMPBGS「恢复数据」按钮失效——问题分析与修复方案

> 版本 v1.0 · 2026-10-17 · 供技术决策评估用
>
> **结论先行**：数据未丢失；控制台「恢复数据」按钮在当前操作路径下必然静默失败；根因是三个脚本对“停止”的语义不一致。立即恢复只需手动执行一条恢复命令；永久修复有 A/B/C 三个方向（含组合建议），见第 5 节对比后决策。

---

## 1. 背景

**产品**：BB 密评协同管理系统（BMPBGS），Windows 单机部署，Node + Express + PostgreSQL 18。脚本组成：

| 脚本 | 职责 |
|---|---|
| `bb-control.ps1` | 控制台（WinForms）：启动系统 / 停止系统 / 打开系统 / 备份数据 / 恢复数据 / 退出 |
| `bb-start.ps1` | 端口避让、首次 initdb、拉起 PostgreSQL + Node 后端 + 前端静态服务 |
| `bb-stop.ps1` | 结束前后端进程，**并停止 PostgreSQL** |
| `bb-backup.ps1` | pg_dump 自定义格式 + robocopy 拷贝 storage/uploads 到 `数据目录\backups\<时间戳>` |
| `bb-restore.ps1` | 终止连接 → DROP/CREATE DATABASE → pg_restore → 回拷 storage/uploads |
| `bb-common.ps1` | 公共函数：路径解析、配置读写、实例身份校验 |

**部署形态**：安装版程序目录 `D:\BMPBGS`，独立数据目录 `D:\BMPBGS-Data`（pgdata / storage / uploads / backups），由程序目录下的 `bb-data-path.txt` 记录数据路径。端口：PostgreSQL 54328、后端 API 3100、前端 5173。

**事发操作**：用户手动删除 `D:\BMPBGS-Data` 下的 `pgdata` 与 `storage` 两个目录 → 控制台点击「恢复数据」→ 两目录“回来了” → 点击「启动系统」并打开网页 → **项目列表为空**。

---

## 2. 现象与直接结论

1. **数据没有丢**。备份集 `D:\BMPBGS-Data\backups\20261016-161317` 完好：23MB dump、pg_restore -l 可列出 89 条目录项，projects / users / project_members / project_stage_records / assessment_records / asset_items / risks / evidence_files / audit_logs / system_settings 十张表的 TABLE DATA 齐全。
2. **「恢复数据」实际一次都没有执行成功**。用户看到的 pgdata/storage 目录，是随后点「启动系统」时程序自动重建的“空壳”。
3. 当前系统连的是一个当天 22:59 自动 initdb 的空数据库：projects=0、users=11（纯种子账号）、system_settings=2，其余业务表全部 0 行。

---

## 3. 原因：失败链与证据

### 3.1 失败链（按时间顺序）

1. 用户先停止系统。`bb-stop.ps1` 第 39 行在结束前后端进程后，还会执行 `pg_ctl -D <pgdata> stop -m fast`——**PostgreSQL 被一起停掉**。
2. 用户删除 pgdata 与 storage 目录（此时 PG 已停，删除成功）。
3. 用户点击「恢复数据」。`bb-control.ps1` 第 237-262 行的按钮逻辑**只检查 web(5173)/api(3100) 端口是否释放，不检查 PG**；端口已释放 → 放行，后台以 `-Silent` + 隐藏窗口方式运行 `bb-restore.ps1`。
4. `bb-restore.ps1` 第 49-57 行：恢复前必须连上 54328 的 PostgreSQL 校验实例身份（`SHOW data_directory` 与期望 pgdata 比对，防止误删别的实例的库）。**PG 没在运行 → 校验返回 $null → 脚本报“无法校验 PostgreSQL 实例身份”并 exit 1**。数据库没有恢复，storage 文件没有回拷。错误藏在隐藏窗口里，用户完全看不到。
5. 用户点击「启动系统」。`bb-start.ps1` 第 72-83 行发现 `pgdata\PG_VERSION` 不存在 → 调用 `database\setup.ps1` **initdb 一个全新空集群**（文件时间戳 22:59:24）→ 补种 seed.sql（users=11）→ 第 145-150 行把安装目录里的 `storage\templates` 复制到数据目录（22:59）。
6. 用户看到 pgdata/storage“回来了”，误以为恢复成功；打开的系统连的是空库，项目列表为空。

### 3.2 证据

| 证据 | 说明 |
|---|---|
| pgdata 内 PG_VERSION/base 等文件时间戳全部为 22:59:24~36 同一秒级 | initdb 新建空库的特征；真实集群的文件时间戳跨度很大 |
| postgresql.log 仅 22:59:33、23:00:20 两次启动记录，首个集群无历史数据 | 当前集群是 22:59 新建的 |
| `D:\BMPBGS-Data\storage` 只有 templates，没有备份集里那份 67MB 的 projects | 恢复脚本第 67-70 行的 robocopy 回拷步骤从未执行 |
| 当前库 projects=0、users=11、system_settings=2，其余表 0 行 | 纯种子数据 |
| bb-restore.ps1 第 49-53 行：连不上 PG 即报错退出 | 恢复未执行的结构性原因 |

### 3.3 设计缺陷本质

三个脚本对“停止”的语义不一致，形成死锁：

- `bb-control.ps1` 恢复按钮假设的“可恢复状态” = 前后端已停、**PG 仍在运行**（它只查 web/api 端口）；
- `bb-stop.ps1` 的“停止系统” = 前后端 + PostgreSQL **全停**；
- `bb-restore.ps1` 要求 PG **必须在线**（身份校验、DROP/CREATE、pg_restore 全部需要连库）。

用户按控制台按钮的正常指引操作（停止 → 恢复），必然走进失败分支；且失败不可见——`bb-control.ps1` 第 61-64 行的 `Invoke-ScriptSilent` 用 `Start-Process` 不带 `-Wait`，不检查退出码。

另有一个任何方案都绕不开的场景：**pgdata 被整个删掉时 PG 无法启动，必须先 initdb**（该逻辑目前只存在于 `bb-start.ps1`）。

## 4. 立即恢复（本文撰写时状态：PG 正在运行、系统开着）

两条路线任选，效果相同。

### 路线 1（推荐，系统开着直接恢复）

PowerShell 执行：

```powershell
powershell -ExecutionPolicy Bypass -File "D:\BMPBGS\bb-restore.ps1" -BackupSet "D:\BMPBGS-Data\backups\20261016-161317" -Silent
```

bb-restore.ps1 内部会先 `pg_terminate_backend` 踢掉后端连接再恢复，node 连接池自动重连；稳妥起见恢复完成后在控制台停/启一次系统，浏览器 Ctrl+F5 强刷。

### 路线 2（坚持用控制台按钮）

1. 控制台点「停止系统」；
2. PowerShell 执行：
   ```powershell
   & "D:\BMPBGS\pgsql\bin\pg_ctl.exe" -D "D:\BMPBGS-Data\pgdata" -l "D:\BMPBGS-Data\pgdata\postgresql.log" start
   ```
3. 控制台点「恢复数据」（此时 web/api 已释放、PG 在跑，按钮放行，正常恢复）；
4. 恢复完成后点「启动系统」。

### 恢复后注意事项

- 备份是 16:13 的快照，16:13 之后新录入的数据不在其中（当前是空库，实际无损）；
- 该备份存在已知的“库与 storage 错位”（dump 是源码集群当天数据，storage 是安装版 10-08 旧目录），恢复后早期 4 个老项目的附件目录可能对不上，新项目不受影响；
- 目前全盘仅此一份备份集，恢复成功后请立即用控制台「备份数据」重新备份。

## 5. 永久修复：三个方向对比

### 方向 A：bb-restore.ps1 自愈（恢复前确保 PG 在线）

**做法**：在第 49 行身份校验之前，检测 54328 无监听时先用 `pg_ctl -D $p.PgData -l ... start` 拉起 PG 并等待就绪（`bb-start.ps1` 第 88-100 行有现成模式可抄）。
- **A1**：仅自动拉起 PG（pgdata 仍在时管用）；
- **A2**：pgdata 不存在时先 initdb 再拉起（覆盖本次事故完整场景；需把 bb-start.ps1 第 72-83 行的 initdb 逻辑抽到 bb-common.ps1 共用，否则重复实现两处）。

| 优势 | 劣势 |
|---|---|
| 用户操作路径不变（停止→恢复→启动），零学习成本 | 脚本变重；A2 要动 bb-common.ps1，改动面扩大 |
| 手动跑命令的用户同样受益 | 自动 initdb/启动属于隐式动作，与“先停止再恢复”的显式安全语义略有张力 |
| 未来“恢复前自动备份当前库”等逻辑可集中在一处 | 恢复完成后 PG 保持运行（无害，bb-start 已兼容该状态） |
| 不动控制台 UI、不动既有安全校验 | 两处 initdb 逻辑有漂移风险（若不抽公共函数） |

### 方向 B：控制台按钮不强制停止

**做法**：删除/放宽 `bb-control.ps1` 第 239-243 行对 web/api 端口的拦截，改为提示不拦截（bb-restore.ps1 自身有 terminate 逻辑，在线可恢复）。

| 优势 | 劣势 |
|---|---|
| 改动最小（一段判断），恢复按钮随时可点 | 违反“恢复前停止服务”的安全直觉：在线用户被踢、正在上传/下载的文件可能被 robocopy 占句柄 |
| 恢复后不用重启系统（连接池自动重连） | 运维指南（`docs/BMPBGS-安装与数据迁移备份恢复指南.docx/.md`）中“恢复前先停止系统”的表述作废，需同步改 |
| 与 bb-restore.ps1 现有能力配套 | 后端偶发请求报错可能被用户误认为系统故障 |

### 方向 C：bb-stop.ps1 拆分停止粒度

**做法**：bb-stop.ps1 增加 `-KeepPostgres` 开关（或控制台新增“仅停服务”按钮），停止时保留 PG。

| 优势 | 劣势 |
|---|---|
| 语义最干净：“停服务”与“停数据库”本就是两件事 | 控制台 UI 要加按钮/选项（760px 面板已排 6 个按钮，需重排） |
| 不动 bb-restore.ps1 任何安全语义 | 用户需理解两种停止的区别，有学习成本 |
| Linux 侧脚本（`linux/`）可同步受益 | **单独使用覆盖不了本次事故**：pgdata 被删后 PG 不在跑，“仅停服务”后点恢复照样失败，仍需先「启动系统」initdb |
| 运维指南需同步更新 | |

### 组合建议

- **A1 + B（推荐）**：A1 覆盖“停了系统就点恢复”这条最常见踩坑路径；B 让系统开着也能直接恢复。两条路都通，用户怎么顺手怎么来；改动合计约 30 行，不动 UI。“pgdata 被删”的极端场景仍靠先点一次「启动系统」initdb 解决——恢复脚本保持单一职责，initdb 归启动脚本管，边界清晰。
- **若只改一处，选 A1**：手动命令与按钮两条路径都覆盖，且不触碰任何安全语义。
- **C** 适合作为控制台向专业运维方向演进的后续项，当前性价比最低。

## 6. 决策约束（供评估参考）

1. **既有安全语义不能破坏**：bb-restore.ps1 第 49-57 行的实例身份校验（防止误删/误覆其他 PostgreSQL 实例的库）必须保留；bb-backup.ps1 的备份前校验同理。本机历史上存在两套实例共用 54328 互相排斥的问题，这些校验正是为此而加。
2. **.ps1 脚本必须保存为 UTF-8 BOM**，否则 Windows PowerShell 5.1 按 GBK 误读中文报语法错误。
3. **程序有两份副本需同步**：源码工程 `E:\02密评\BBMPGJ\MPJG-CODEX-MASTER` 与安装版 `D:\BMPBGS`（运行时以后者为准）。
4. **“失败不可见”是放大器**：`bb-control.ps1` 的 `Invoke-ScriptSilent` 不等待、不检查退出码。无论选哪个方向，都建议顺带修复（-Wait -PassThru + ExitCode，或把后台输出落日志文件）。
5. **备份策略现状**：仅一份备份集；恢复成功后应立即重新备份。

## 8. 最终决策（2026-10-17）

采用 **A2 + C 的内部停止粒度 + 可见执行结果**，不采用在线恢复方案 B：

1. 「恢复数据」自动停止 Web/API，保留或自动启动 PostgreSQL；`pgdata` 不存在或为空时初始化最小集群。
2. 保留 PostgreSQL 实例身份校验；目录非空但缺少 `PG_VERSION` 时拒绝自动初始化。
3. 数据库先恢复到临时库，`storage/uploads` 先复制到临时目录，校验成功后统一切换，失败自动回退。
4. 控制台允许选择备份集，默认选中最新备份；历史无清单备份继续兼容。
5. 备份与恢复脚本的输出、退出码和日志由控制台跟踪，失败不再静默。
6. 控制台取消始终置顶、支持缩放和日志查看；右上角 `X` 只关闭控制台，不停止后台服务。
