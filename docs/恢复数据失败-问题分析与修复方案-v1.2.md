## 一、背景

用户使用最新打包的安装包（安装路径 `D:\BBmpinstall`，程序目录 `D:\BBmpinstall\BMPBGS`，数据目录 `D:\BBmpinstall\MPDATA`，实例 ID `installed-a788ffdf`，端口 PostgreSQL=54328 / 后端=3100 / 前端=5173），通过控制台「历史记录」对备份集执行恢复操作，控制台提示：

```
任务执行失败：restoring，退出码 。
[15:19:08]  正在恢复备份集：20261016-161317
[15:19:09]  正在预检备份集：D:\BBmpinstall\MPDATA\backups\20261016-161317
[15:19:09]  正在停止 Web/API，PostgreSQL 将保持或自动恢复运行...
[15:19:19]  BMPBGS Web/API 已停止，PostgreSQL 保持运行。
[15:19:19]  恢复失败，正在回退：停止 Web/API 失败，退出码：128
```

排查开始后，用户又进行了一轮"备份 → 恢复自己的备份集"实测（15:26:58 备份 `20261017-152658`，15:28:09 恢复），**再次失败，错误完全相同**，证明这是必复现的缺陷而非偶发。

经 `diff` 逐字节比对，安装版 6 个运行脚本与源码仓库 HEAD 完全一致，故缺陷在仓库代码中，非安装包打包问题。

**v1.0 修复后的验证又暴露了第二个失败点**：15:56:57 用户先手动「停止系统」（PG 随之关机），15:58:21 再次恢复 `20261017-152658`——停止步骤本次顺利通过（耗时仅 2 秒，补丁生效），但流程往下走到：

```
[15:58:23]  正在停止 Web/API，PostgreSQL 将保持或自动恢复运行...
[15:58:25]  BMPBGS Web/API 已停止，PostgreSQL 保持运行。
[15:58:37]  正在准备 PostgreSQL...
[15:58:41]  恢复失败，正在回退：检查应用数据库角色 失败，退出码：-1
```

PostgreSQL 日志（`postgresql.log`）显示 15:58:38.92 PG 被重新拉起、15:58:39.07 即"ready to accept connections"——**数据库本身是好的**，失败发生在 PG 就绪约 2 秒后的角色检查步骤。退出码 **-1** 不是 psql 的常规退出码（1=自身错误 / 2=连接失败 / 3=脚本错误），这是第二个缺陷的特征。

**v1.1 修复后的验证又暴露了第三个失败点：脚本挂起、控制台无法关闭**。16:20 用户报告控制台弹窗"当前维护任务仍在执行，请等待完成后再关闭控制台"，无法关闭。排查发现：

- 15:58:21 启动的恢复子进程（PID 10820）**27 分钟后仍未退出**，控制台的关闭保护因此一直拦截（保护本身行为正确）；
- 该进程卡在一个 22 分钟未退出的 psql（PID 30420，回退步骤的 `DROP DATABASE IF EXISTS bb_restore_<tag>`）上；
- 而该临时库**从未被创建**（失败发生在建库之前），这条 DROP 本应是瞬间完成的空操作。

应急处理：终止挂起的 psql（对不存在的库执行 no-op DROP，零数据风险）→ 恢复脚本续跑完回退并正常退出 1 → 控制台放行。同时清理了 15:26 遗留的备份僵尸进程（PID 6068，无 `-Silent` 参数卡在 `Read-Host`）。修复脚本后，16:30:14 恢复 `20261017-152658` **全流程成功**。

## 二、根因分析

### 2.1 直接根因：停止脚本把 pid 文件里的"端口行"当成进程 PID

`bb-start.ps1` 启动时写入的 `processes.pids` 实际是 5 行（路径：`%TEMP%\bb-miping\<实例ID>\processes.pids`）：

```
backend=12884
frontend=29988
pgPort=54328
apiPort=3100
webPort=5173
```

而 `bb-stop.ps1` 解析该文件用的正则是宽匹配：

```powershell
if ($_ -match '^(\w+)=(\d+)$') {
  $pidv = [int]$Matches[2]
  & taskkill /PID $pidv /T /F 2>$null | Out-Null
}
```

`^(\w+)=(\d+)$` 对 5 行**全部命中**——`pgPort=54328`、`apiPort=3100`、`webPort=5173` 这三个**端口号**被当成了进程 PID 执行 `taskkill /PID 54328 /T /F`。

### 2.2 传导链：taskkill 退出码 128 泄漏，恢复脚本误判

1. 54328/3100/5173 这些"进程"不存在，**taskkill 对"找不到进程"返回退出码 128**（已在真实 PowerShell 环境实测确认；注意：在 Git Bash 的 MSYS 层里该值会被篡改为 1，用 bash 测试退出码语义会得到假结论）；
2. 循环中最后一个 taskkill 留下的 128 停留在 `$LASTEXITCODE`，而 `bb-stop.ps1` 结束时**不清零**，顺着调用链泄漏出去；
3. `bb-restore.ps1` 恢复流程第一步是 `& bb-stop.ps1 -Silent -KeepPostgres`（只停 Web/API、保留 PG），紧接着 `Assert-BBNativeSuccess '停止 Web/API'`（`bb-common.ps1` 中的助手：`$LASTEXITCODE -ne 0` 即 throw）；
4. 于是恢复在**尚未创建临时库、尚未暂存 storage 的第一步**就抛出"停止 Web/API 失败，退出码：128"，进入 catch 回退分支：回退时发现临时库本就没建（`NOTICE: database "bb_restore_... does not exist, skipping`），原库原封不动，最终 `Write-Error` + `exit 1`，控制台报"任务执行失败：restoring"。

### 2.3 附带隐患：可能误杀无关进程

`taskkill /PID x /T /F` 中的 PID 3100、54328 是 4 的倍数（Windows 合法 PID 均为 4 的倍数），**机器上完全可能存在恰好占用这两个 PID 的无辜进程**，一旦存在就会被连进程树强杀。5173 不是 4 的倍数，不可能是活 PID，必然返回 128。本次两次事故未报告误杀，属侥幸。

### 2.4 次要问题：控制台把成功任务也报成"任务执行失败"

控制台日志显示，**每一个**后台任务（starting / stopping / backingup / restoring）结束后都打印：

```
任务执行失败：<kind>，退出码 。
```

注意退出码位置是**空的**。包括：

- 15:18:10 的备份——实际**成功**（备份集 `20261017-151810` 完整落盘：6.5MB dump + storage + uploads + 清单），控制台却报失败——这就是用户"备份失败了"印象的来源；
- 15:20:07 的启动——实际成功（"启动成功，网页和后端均已就绪。"），同样报失败；
- 15:19 的恢复——确实失败（脚本明确 `exit 1`），退出码依然显示为空。

即：控制台 `Update-ControlTask` 里 `$process.ExitCode` 在本机环境读出为空值，`$code -eq 0` 不成立，永远落入失败分支。该现象的底层机理未能定位（排查沙箱禁止派生进程，`Start-Process` 与 `[Diagnostics.Process]::Start` 均被安全策略拦截，无法实证），因此采用防御性修复而非根因修复。相关佐证：`bb-backup.ps1` 结尾并无 `$LASTEXITCODE = 0` 重置，robocopy 的位图退出码（1=复制了文件）本应泄漏成进程退出码 1，但控制台读到的仍是空——说明问题出在控制台读取侧而非子进程退出码本身。

### 2.5 第二个失败点（v1.1 新增）：native 命令直连 `Select-Object -First 1` 管道，退出码被污染为 -1

`bb-common.ps1` 中有两处把 **native 命令**（psql）直接管道给 `Select-Object -First 1`：

```powershell
# Get-BBTargetInstanceDataDir（PG 实例身份校验）
$actual = (& $Psql ... -tAc "SHOW data_directory" 2>$null | Select-Object -First 1)
# Ensure-BBAppRole（应用角色检查，即失败点）
$exists = (& $psql ... -tAc "SELECT 1 FROM pg_roles WHERE rolname='bb_miping_app'" 2>$null | Select-Object -First 1)
Assert-BBNativeSuccess '检查应用数据库角色'
```

**机理（已在运行中的 PG 上实证复现）**：`Select-Object -First 1` 收到第一行输出后立即停止上游管道，PowerShell 会把**尚未退出**的 native 进程杀掉——.NET 的 `Process.Kill()` 以 **-1** 为退出码，于是 `$LASTEXITCODE` 被污染为 -1。实测该竞态多数次发生（连续 3 次中 2 次得到 -1，偶发 1 次 psql 抢在自己被杀前正常退出得到 0）；连接失败场景（如端口不通）psql 死得早，退出码 2 反而能保留。

**为什么以前没暴露**：恢复流程在 v1.0 修复前第一步（停止）就失败退出，根本走不到角色检查；而更早的身份校验（`Get-BBTargetInstanceDataDir`）虽然同样中招，但它**不检查退出码**、只关心输出文本，所以污染值一直不可见。`Ensure-BBAppRole` 是整个恢复流程中第一个"native 管道之后断言退出码"的地方，缺陷由此首次现形。

### 2.6 第三个失败点（v1.2 新增）：库函数删除调用方的 `PGPASSWORD`，回退 psql 在隐藏窗口中永久等待

`bb-common.ps1` 的 `Start-BBPostgres` 与 `Ensure-BBAppRole` 都在内部设置 `PGPASSWORD` 并在 `finally` 中**直接删除**：

```powershell
$env:PGPASSWORD = $PgPassword
try { ... }
finally { Remove-Item Env:\PGPASSWORD -ErrorAction SilentlyContinue }
```

而 `bb-restore.ps1` 在脚本级（`try` 块之前）设置过一次 `$env:PGPASSWORD = $PgPassword`，并依赖它在后续所有 SQL 操作中持续有效。于是：

1. `Start-BBPostgres`（126 行）返回时删掉 `PGPASSWORD`；
2. `Ensure-BBAppRole`（129 行）内部重设后再删掉；
3. 15:58:41 角色检查抛出（退出码 -1）进入 `catch` 回退分支，回退要执行 `DROP DATABASE IF EXISTS $tempDb`——**此时已无 `PGPASSWORD`**；
4. psql 连接 PG 时 `pg_hba` 要求 scram 口令 → psql 在控制台 `-NonInteractive -WindowStyle Hidden` 子进程里**交互式等待输入口令** → 永远等不到 → 整个恢复进程挂死。

**更深一层**：即便本次不在角色检查失败，主流程里 `Start-BBPostgres` 之后的所有 `Invoke-RestoreSql`（建临时库、pg_restore 校验等）都会因同样的原因挂起——这颗雷必然会在下一步引爆。

**为什么 15:19/15:28 的回退没挂**：那两次失败发生在 `Start-BBPostgres` 被调用之前，脚本级设置的 `PGPASSWORD` 还在。

### 2.7 附带问题（v1.2 新增）：控制台成功标记不校验任务种类，把失败恢复报成"恢复成功完成"

`bb-control.ps1` 的 `Update-ControlTask` 判定任务成功时只认前缀：

```powershell
$taskOk = [bool]($taskOutput | Where-Object { $_ -match '^BB_TASK_OK=' })
```

而恢复流程内部会调用 `bb-stop.ps1`，后者会输出自己的 `BB_TASK_OK=stopping` 并出现在**恢复任务的**输出流中。结果 16:25:29 控制台日志显示：

```
[16:25:29]  恢复成功完成；请点击“启动系统”。
```

而这次恢复实际是失败的（`exit 1`）。嵌套脚本的成功标记污染了宿主判定。

## 三、修复方法（提交 `a0c41eb` 退出码 128 + `7968e9f` 退出码 -1 + `75347bc` 挂起与误报，均在 main 分支）

### 3.1 `bb-stop.ps1`——根因修复（退出码 128）

- pid 文件解析改为只认进程键：`^(backend|frontend)=(\d+)$`，端口行一律跳过（端口避让由既有的"按监听端口兜底"机制负责，本就覆盖该场景）；
- 进程处理段末尾显式 `$global:LASTEXITCODE = 0`——taskkill"进程不存在"（128）对停止操作是预期结果，不允许泄漏给调用方；
- 成功路径输出 `BB_TASK_OK=stopping` 标记。

### 3.2 `bb-restore.ps1`——把"断言"换成"实证"

- 删除会被 taskkill 污染的 `Assert-BBNativeSuccess '停止 Web/API'`；
- 改为**校验端口实际释放**：`Get-NetTCPConnection -LocalPort <apiPort|webPort> -State Listen`，最多重试 5 秒，仍在监听才 throw"停止 Web/API 失败：端口 X 仍在监听"。语义从"猜"变成"看事实"；
- 成功路径输出 `BB_TASK_OK=restoring`，结尾显式 `exit 0`。

### 3.3 `bb-start.ps1` / `bb-backup.ps1`——确定性退出码 + 成功标记

- 成功路径（健康检查通过 / 本地备份完成且 NAS 无失败）输出 `BB_TASK_OK=<kind>` 并显式 `exit 0`；
- NAS 上传失败的 `exit 2` 分支位于标记之前，不受影响；
- 显式 `exit 0` 使 robocopy 位图退出码、pg_ctl 等 native 退出码不再泄漏成进程退出码。

### 3.4 `bb-control.ps1`——控制台判定逻辑

- `Read-ControlTaskOutput` 的过滤行加入 `TASK_OK`（标记不展示给用户）；
- `Update-ControlTask` 成败判定改为：**`BB_TASK_OK` 显式标记为第一判据，退出码兜底**（`$taskOk -or ($codeReadable -and $code -eq 0)`）；
- 退出码读不到（空）时，新增"任务已结束，但无法确认执行结果（退出码不可用）。请依据以上日志判断"的蓝色提示分支，不再红字假报失败；
- `exit 2`（NAS 失败）分支增加 `$codeReadable` 前置，避免空值误入。

### 3.5 `bb-common.ps1`——native 命令禁用直连 `Select-Object -First 1`（提交 `7968e9f`）

- `Get-BBTargetInstanceDataDir` 与 `Ensure-BBAppRole` 两处均改为**先收集全部输出、再取第一行**：

```powershell
$roleLines = @(& $psql ... -tAc "SELECT 1 FROM pg_roles WHERE rolname='$AppUser'" 2>$null)
Assert-BBNativeSuccess '检查应用数据库角色'
$exists = if ($roleLines.Count -gt 0) { $roleLines[0] } else { $null }
```

- `@()` 数组收集不会提前停止管道，psql 正常退出，`$LASTEXITCODE` 是该进程的真实退出码（0=成功 / 2=连接失败），断言语义恢复可信；
- 全仓排查确认：其余 `Select-Object -First 1` 均作用于 PowerShell cmdlet 或已收集的变量（如 `bb-restore.ps1` 的 `$result | Select-Object -First 1`），无 native 进程参与，安全。

### 3.6 `bb-common.ps1` + `bb-restore.ps1`——修复脚本永久挂起（提交 `75347bc`）

1. 两个库函数的 `PGPASSWORD` 由"用完删除"改为**保存调用方原值、结束时还原**：

```powershell
$callerPgPassword = $env:PGPASSWORD
$env:PGPASSWORD = $PgPassword
try { ... }
finally {
  if ($null -ne $callerPgPassword) { $env:PGPASSWORD = $callerPgPassword }
  else { Remove-Item Env:\PGPASSWORD -ErrorAction SilentlyContinue }
}
```

   （`bb-start.ps1` 属于"调用方未设置"的场景，仍走删除分支，行为不变。）

2. `bb-restore.ps1` 的 `catch` 回退分支**显式兜底重设** `$env:PGPASSWORD = $PgPassword`（纵深防御：任何异常路径下回退 SQL 都不会缺口令）。

### 3.7 `bb-control.ps1`——成功标记校验任务种类（提交 `75347bc`）

```powershell
$taskOk = [bool]($taskOutput | Where-Object { $_ -match "^BB_TASK_OK=$kind\s*$" })
```

只认与当前任务种类一致的标记，嵌套 `bb-stop` 的 `BB_TASK_OK=stopping` 不再能让失败的恢复显示成成功。

## 六、经验教训（可复用）

1. **`$LASTEXITCODE` 是全局污染源**：任何调用 native 命令（taskkill/pg_ctl/robocopy/psql）的 PowerShell 脚本，只要可能被其他脚本用 `&` 调用并用退出码判断成败，就必须在结尾显式清零或显式 `exit`。robocopy 位图退出码（1）、taskkill"进程不存在"（128）都是典型的"假失败"码。
2. **pid 文件不要混存端口**：若必须混存，解析端必须用键名白名单，禁用 `^(\w+)=(\d+)$` 这类宽正则；更稳妥的设计是进程与端口分两个文件。
3. **不要用 taskkill 的退出码判断"停止是否成功"**：停止操作中"进程已不存在"就是成功；判断停止是否成功应该看端口是否还在监听。
4. **控制台读子进程退出码在本机 WinForms + Start-Process -PassThru + 重定向环境下不稳定（读出为空）**：后台任务的成败不能单独依赖进程退出码，应由任务脚本输出显式结果标记（本项目统一为 `BB_TASK_OK=<kind>`），宿主以标记为第一判据。
5. **测试 native 命令退出码语义必须用真实 PowerShell**：Git Bash 的 MSYS 层会篡改部分退出码（如 taskkill 128 → 1），在 bash 里得出的结论不可信。
6. **native 命令禁止直连 `Select-Object -First 1` 管道**：提前停止管道会杀掉尚未退出的进程，`$LASTEXITCODE` 被污染为 -1（.NET Kill 退出码），且输出往往还是对的——属于"结果正确、退出码错误"的最危险一类 bug。正确写法是 `@(& native ...)` 先收集再取 `[0]`，或先赋值给变量再管道。
7. 恢复类操作遵循"失败尽早、破坏靠后"原则本次得到了正面验证：三步失败都发生在触碰数据之前，自动回退逻辑（含临时库不存在时的 NOTICE 跳过）工作符合预期。
8. **库函数不得删除调用方的环境变量**：临时改写 `PGPASSWORD` 之类变量时，必须"保存原值 → 结束时还原（未设则删除）"，否则会破坏调用方的隐式依赖。本项目因此出现"回退 psql 缺口令 → 隐藏窗口交互等待 → 脚本永久挂起 → 控制台无法关闭"的连锁故障。
9. **无人值守脚本里禁止任何可能进入交互等待的调用**：psql 缺口令会提示输入、`Read-Host` 会等人——在 `-NonInteractive -WindowStyle Hidden` 的子进程里这些都永远不会返回。应急时只能杀掉卡住的 native 子进程（对不存在的对象执行 no-op 操作时零风险），再让脚本自己走完收尾。
10. **嵌套脚本的成功标记必须绑定任务种类**：宿主判定任务成败时若只匹配 `^BB_TASK_OK=` 前缀，内嵌 `bb-stop` 的 `BB_TASK_OK=stopping` 会把失败的恢复显示成成功。标记要带种类，宿主要比对种类。
