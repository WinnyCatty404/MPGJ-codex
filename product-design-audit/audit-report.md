# 密评工具「测评实施」页面设计审查

## 审查范围

- 页面：`prototype.html` 项目测评实施工作区
- 流程：项目准备 → 测评准备与方案编制 → 现场测评 → 报告编制 → 报告导出
- 用户目标：快速理解当前阶段，录入/复核大量测评信息，并稳定产出报告
- 证据：本次审查现场截取的 5 个阶段窄窗口画面

## 总体判断

产品流程本身是清楚的，自动保存、阶段进度和报告出口也建立了信任感。主要问题不是颜色不够漂亮，而是桌面表格结构在窄窗口中没有重新排版：顶部操作、阶段条、二级导航和内容表格同时横向滚动，导致阅读顺序断裂、字段截断、中文被迫竖排。

建议先重构响应式信息架构，再统一视觉语言。只换配色、阴影和圆角无法解决当前的核心体验问题。

## 五个阶段

### 1. 项目准备 — 需要改进

优点：单位信息、联系人信息、机构信息的分组明确；保存状态可见。

问题：顶部操作和阶段条被截断；双列表单在窄屏仍保持两列，长内容不可见；只读机构信息与可编辑表单的视觉区分不足。

建议：桌面保持两列，窄屏切为单列；将只读机构信息做成浅色摘要卡；底部保存区做成固定操作栏，并把“重置”降为次要操作。

### 2. 测评准备与方案编制 — 高风险

优点：内容目录完整，能覆盖复杂方案材料。

问题：左侧章节、顶部子标签和表格构成三套导航；表格列在窄屏被压扁，标签竖排且内容不可读；用户很难判断完成进度和下一处待填项。

建议：桌面使用固定左侧章节导航 + 主内容卡片；窄屏改成“当前章节下拉 + 分组折叠面板”。每个章节显示完成率、错误数和缺失项，并提供“下一未完成项”。

### 3. 现场测评 — 高风险

优点：结果记录、证据、DAK 与得分放在同一业务上下文里。

问题：复杂数据表在窄屏中基本不可操作；固定列宽导致标题竖排；结果文本、证据上传和评分控件竞争空间；页面底部的判定规则很长且难以随时参照。

建议：桌面保留数据网格并冻结“测评单元/对象”两列；窄屏改成“一条测评对象一张卡”，结果、证据、DAK 评分分层展开。将判定规则放入可随时打开的帮助抽屉，并用状态徽标替代单纯符号。

### 4. 报告编制 — 中等风险

优点：把报告拆成分析、结论、评价、建议和附录，符合用户的工作心智。

问题：主阶段、报告章节、安全层面形成三层标签；当前层级不容易辨认；安全层面按钮组占据大量首屏空间，正文出现得太晚。

建议：桌面用左侧报告目录，正文顶部只保留当前安全层面切换；窄屏用两个下拉选择器替代多排标签。正文前增加“已生成/待复核/有风险”摘要，让用户先看状态再读长文。

### 5. 报告导出 — 基本健康

优点：卡片、格式图标、说明和按钮已经形成清晰层级，是五个阶段里最接近成熟产品的一页。

问题：标题说明在窄屏仍显拥挤；不同导出动作的主次不够明确；缺少生成进度、最近生成时间和产物状态。

建议：把 Word 设为默认主操作，PDF 和原始记录作为次级卡片；增加“最近生成”“模板版本”“生成中/成功/失败”状态；按钮统一宽度与位置。

## 建议的视觉方向

1. 使用深海军蓝作为结构色、明亮蓝作为唯一主操作色、绿色只表达成功，减少同时出现的蓝色层级。
2. 页面背景使用很浅的冷灰，编辑区放入白色卡片；卡片圆角约 10–12px，边框优先于重阴影。
3. 采用稳定的 8px 间距体系；标题、说明、标签和值形成明确的四级文字层级。
4. 顶部只保留项目上下文、自动保存状态和核心操作；阶段导航与页面内容之间增加更明显的间距和分隔。
5. 表单控件最小高度约 40–44px；长字段占整行，短字段才并排；错误、必填和只读状态要有完整文字提示。

## 无障碍风险

- 窄列导致文字竖排和截断，影响阅读顺序和缩放后的可用性。
- 多个横向滚动容器会给键盘和触控用户带来导航困难。
- 灰色辅助文字与浅色边框存在对比度不足风险。
- 自动保存状态不应只依赖绿色圆点，应保留文字和可读状态。
- 需要继续验证键盘焦点、标签与控件关联、错误提示播报和 200% 缩放；截图本身不能证明 WCAG 合规。

## 优先级

1. 先解决窄窗口响应式结构和多层横向滚动。
2. 再统一导航层级：主阶段、章节、安全层面各只保留一种清晰模式。
3. 将复杂表格设计成桌面网格 + 窄屏卡片两套呈现。
4. 最后统一颜色、字体、间距、圆角、按钮和状态组件。
